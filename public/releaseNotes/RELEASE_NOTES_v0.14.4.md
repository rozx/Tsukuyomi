## 🗑️ 删除确认文本归一化 (Confirmation Text Normalization)

从网页爬取的书名经常带有肉眼无法察觉、键盘也敲不出来的字符（零宽空格、全角空格、Unicode 分解形式的浊音符号等）。旧版删除确认只做 `trim()` 后的严格相等比较，遇到这类书名时无论怎么输入都会提示「标题不匹配」，书籍被卡在库里删不掉。

本版本新增 `normalizeConfirmationText` / `isConfirmationTextMatch`（`src/utils/text-utils.ts`），确认框比较前对**输入与目标名称同时**做归一化：

- **Unicode NFC 规范化**：剪贴板与部分 IME（尤其 macOS 日文输入）会产出 NFD 分解形式，例如「で」= `て(U+3066)` + `浊音符号(U+3099)`，视觉完全相同但码位不同，严格比较必然失败
- **剥离零宽字符**：BOM / ZWSP / ZWNJ / ZWJ（`U+200B`–`U+200D`、`U+FEFF`）在抓取的标题里很常见，用户无法用键盘复现
- **全角空格折半**：`U+3000` → 半角空格，用户手打时几乎只会打出半角空格
- **首尾 trim**：保留原有的首尾空白容忍

同时收紧了一处安全边界：**目标名称归一化后为空时一律判定为不匹配**，避免标题缺失的条目被一个空输入直接删掉。

`isDeleteDisabled` 与实际删除动作共用同一份判定逻辑，按钮可点即代表能删，不会再出现「按钮亮着但点了报标题不匹配」的错位。

- **测试覆盖**：新增 `confirmation-text-match.test.ts`，覆盖首尾空白、全角空格、零宽字符、NFC/NFD 等价、空目标名称拒绝等边界场景

## 📝 问题修复

- 修复：书籍标题含首尾空白 / 全角空格 / 零宽字符时，删除确认框输入正确书名仍提示「标题不匹配」，导致书籍无法删除
- 修复：标题为 NFD 分解形式（如日文浊音假名）时，从剪贴板粘贴的正确标题无法通过删除校验
- 修复：删除按钮的禁用判定与实际删除校验各写一份 `trim()` 比较，边界场景下二者结论可能不一致
