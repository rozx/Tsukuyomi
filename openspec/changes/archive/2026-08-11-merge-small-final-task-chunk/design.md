## Context

翻译、润色和校对最终都由 `text-task-processor.ts` 调用 `chunk-formatter.ts` 构建任务 chunk。翻译使用 `buildFormattedChunks`，润色和校对直接使用 `buildChunks`；前者内部同样委托给后者。任务重试或部分段落已完成时，也会通过相同闭包重新构建剩余 chunks。

现有算法在加入下一段会超过 `chunkSize` 时结束当前块，因此章节末尾可能形成只有少量文本的独立块。每个块都有固定的上下文构建、模型连接和工具循环成本。

## Goals / Non-Goals

**Goals:**

- 对翻译、润色和校对统一消除小于配置大小三分之一的独立尾块。
- 保持格式化文本、段落顺序、段落 ID 与工具边界一致。
- 让初次分块和剩余段落重建使用完全相同的规则。
- 用严格边界测试固定“小于合并、等于不合并”的语义。

**Non-Goals:**

- 不对所有低利用率 chunk 做全局重新平衡。
- 不拆分单个超长段落，也不改变已有段落过滤规则。
- 不新增用户设置、数据迁移或任务类型专用阈值。
- 不根据模型 token 估算器动态调整阈值。

## Decisions

### Decision 1: 在共享 `buildChunks` 完成后合并一次尾块

初始分块完成后检查最后两个块；当 `last.text.length * 3 < chunkSize` 时，将尾块并入前一块并移除尾块。这样翻译的 `buildFormattedChunks`、润色、校对和重建路径会自动得到一致行为。

备选方案是在 `text-task-processor.ts` 的处理循环中动态查看下一个块并合并。该方案会让进度总数、chunk 边界和重试重建分别处理额外状态，因此不采用。

### Decision 2: 使用格式化后文本长度判断

阈值沿用现有分块算法使用的 `paragraphText.length` 口径，而不是只计算原文或译文。模型实际接收的索引、ID 标签、原文、译文和分隔符都会计入大小，因而判断与 `chunkSize` 的当前语义一致。

### Decision 3: 合并结果允许超过常规大小且不递归重切

合并的目的就是用一次稍大的请求替代一个很小的独立请求。尾块严格小于配置值三分之一，因此在普通段落不超长的情况下，新增输入有明确上界。合并只发生一次，且只面向最终块；不会向前连续吞并其他块。

### Decision 4: 保持严格小于语义

使用乘法比较 `last.text.length * 3 < chunkSize`，避免浮点除法边界含糊。等于三分之一时保留独立块，与需求中的“小于”一致。

## Risks / Trade-offs

- [Risk] 合并后的请求可能超过用户设定的 `chunkSize`，提高单次响应时间或接近模型输入限制。  
  → Mitigation：额外尾块严格小于设置值三分之一；现有模型最大输入校验与单段超长容忍逻辑保持不变。

- [Risk] 测试或 UI 进度依赖旧 chunk 数量。  
  → Mitigation：在创建处理循环前完成合并，使总块数、进度回调与工具边界都读取最终数组。

- [Risk] 重试只剩少量段落时可能与初次执行形成不同边界。  
  → Mitigation：重试本来就按剩余 ID 重建边界；复用相同构造器可确保规则一致且不丢段落。

## Migration Plan

1. 先增加共享分块函数的失败测试，覆盖小于、等于和大于三分之一的边界。
2. 在 `buildChunks` 返回前实现尾块合并，并验证翻译格式化路径同样生效。
3. 运行相关测试及项目规定的 lint、type-check、quality-check。
4. 本变更不涉及持久化迁移；回滚时移除尾块后处理即可恢复旧行为。
