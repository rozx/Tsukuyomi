# Design

## Context

当前 manifest 每本书只有一个哈希，上传先压缩整书再切块；下载及历史恢复返回完整 Novel，合并依赖章节时间、结构基准和实体删除记录。Gist API 超过 300 文件会截断列表，现有客户端会中止。用户已选择稳定小组方案。

## Goals / Non-Goals

目标：局部章节编辑只影响一个小组；保持跨设备合并、完整恢复、失败重试能力。
不改变 IndexedDB 本地布局，不添加同步提供商或多 Gist 分库，不改变实体删除裁决。

## Decisions

1. 每本书固定 16 组，用 FNV-1a 对 chapter.id 的 UTF-16 code units 哈希，取低 4 位，十六进制组 ID。固定数量避免追加、插入、移动章节导致其他组重排；组内按 ID 排序。空组不存储。
2. `novel:<bookId>` 是书籍/卷/章节元数据，剥离章节 content、originalContent、contentLoaded；v6 存 `book-<id>.json`，必要时 `book-chunk-<id>_N.json` 和 meta。章节正文以 `chapters:<bookId>:<group>` 条目存放，载荷包含 bookId、groupId、chapters（含 id、content/originalContent），文件名前缀 chapters-/chapters-chunk-。保留章节元数据使现有合并协议不变。
3. v6 下载先验证元数据与组载荷哈希，再将变化的正文组装到元数据。某组变化时，即使元数据哈希未变也读取元数据依赖。下载使用当前本地目录检查正文可复用的章节身份，本地缺失的章节即使组哈希未变也补读其正文组。未变化且本地仍存在的章节保持正文缺省，并向 apply 传递明确的未下载章节集合；合并时保留这些章节本地正文/原始文本，不将本地正文误记为远端结构基准。若下载后本地章节又被删除，apply 在保存前拒绝该不完整书籍并保留未确认状态。新设备/恢复读取全部组，缺组、缺章、身份不符或重复 ID 均失败。
4. 旧协议通过 effectiveSchemaVersion 选择旧文件名和整书读取；v6 新文件名使多批迁移中的旧文件保持可读，最后发布清单并删除旧文件。设置、模型、封面与记忆文件同样使用 v6- 前缀，保证迁移时这些集合有本地修改也不会提前覆盖旧清单引用的内容。v5 的规范化哈希校验继续保留，不因当前版本升为 v6 而失效。
5. 复用现有上传批次、压缩、超限分块和并发检查。写前从远端快照或已知布局估算每批文件数，任一批超过 300 均先失败，提示减少同步数据。该限制也适用于多本书/超大章节产生额外分块的情形。
6. 上传后结构基准必须核对章节所在组哈希，不能仅凭元数据哈希认定正文已同步。首次创建沿用已有创建接口，随后使用协议迁移路径；完整性和恢复路径均覆盖无 manifest 的旧初始化布局。

## Risks / Trade-offs

- 小组包含其他章节 → 一次重传该组，换取文件数控制；16 是协议常量，不随书籍增长调整。
- 极大书库仍可能超过 300 文件 → 在写前阻止，保留可读旧数据；不承诺无限容量。
- 部分正文被当成删除/空正文 → 显式区分未下载与真实空正文，并覆盖并发编辑和基准测试。
- 协议迁移中断 → 新文件名与既有升级围栏保护旧布局；保留逐批 ETag/修订检查。

## Migration Plan

升级所有同步设备后首次同步读取旧布局并迁移到 v6；旧客户端依照 schemaVersion 停止普通同步。回滚应用前应恢复升级前的 Gist 修订或本地导出，不让旧客户端强制写入 v6 数据。文档说明一次性迁移上传与小组同步的区别。
