## Why

The mobile redesign was landed by bolting `v-if="isPhone"` branches into the existing desktop pages and the main app shell. As a result, several surfaces now carry two full templates in one Single-File Component — `BookDetailsPage.vue` is ~4950 lines, `TranslationProgress.vue` and `AppRightPanel.vue` are ~1200 lines each, and `MainLayout.vue` mixes phone/tablet/desktop shell branches throughout — which is hard to read, hard to edit safely, and gives us nowhere to put the tablet layout we want next. We want to lock in the three-variant dispatcher pattern (Desktop / Tablet / Mobile) uniformly across every layout and every page before the mobile branch keeps drifting.

## What Changes

- Introduce a **device-variant dispatcher pattern**: each layout and page becomes a thin dispatcher component that mounts one of three variants — `Desktop`, `Tablet`, or `Mobile` — based on `useResponsiveLayout()` (`isPhone` → Mobile, `isTablet` → Tablet, else → Desktop).
- **Electron override — always Desktop.** When running under Electron (`useElectron().isElectron === true`), the dispatcher MUST mount the Desktop variant regardless of window width. Electron is a desktop-only build target; resizing the window smaller must not switch to the Mobile or Tablet variant. This is enforced in the dispatcher (`isElectron ? Desktop : <breakpoint variant>`), not in each variant.
- **DRY — dispatcher logic lives in one place.** The variant-selection rule (Electron override + breakpoint mapping) MUST be implemented once, in a shared helper (e.g., `composables/useDeviceVariant.ts` returning a computed `'desktop' | 'tablet' | 'mobile'`, or a `<DeviceVariant>` component that takes three slots / three component props). Every dispatcher consumes that helper — no dispatcher may re-implement the `isElectron ? ... : isPhone ? ...` conditional by hand. Changing the rule (e.g., adding a new breakpoint) must require editing exactly one file.
- **Apply the pattern to every layout and every page**, with no carve-outs. Layouts and pages are the device-boundary surfaces, so they always ship all three variant files.
- **Extract business logic into per-surface composables** before splitting templates. For each surface being split, any state (`ref` / `reactive`), computed values, async data loading, event handlers, watchers, and lifecycle hooks that are NOT purely about the current viewport layout MUST move into a dedicated composable (e.g., `useBookDetailsPage()`, `useMainLayoutShell()`, `useTranslationProgressPanel()`). The dispatcher or each variant then calls that composable — no variant may re-declare the same state or re-implement the same handler.
- **Variants are view-only.** A variant component is allowed to contain: the `<template>`, a `<script setup>` that (a) imports the surface's composable and destructures what it needs and (b) declares purely local UI state (e.g., a local popover open flag used only by that template), and device-specific `<style>`. Any logic that a future tablet variant would want to reuse MUST already be in the composable.
- **DRY — shared UI fragments are extracted, not copy-pasted.** When the same markup block (a card, a list item, a toolbar button cluster) appears in two or more variants of the same surface, it MUST be extracted into a shared child component under `components/<surface>/` or the surface's own folder. The variant then composes shared fragments with variant-specific layout. Review gate: during implementation, scan each newly-created variant for blocks that appear near-verbatim in a sibling variant; if found, extract before landing the commit.
- **DRY — styles are shared via tokens, not duplicated.** Common color / spacing / border / shadow values use existing Tailwind utilities, design tokens (`--white-opacity-*`, Tsukuyomi palette, `tsukuyomi-blue`), or shared scoped utility classes. Do not duplicate the same hex value or gradient across variant `<style>` blocks — promote it to a token or a shared class.
- **Single source of truth rule.** When a user switches breakpoint at runtime (e.g., rotates a tablet), a variant swap must not reset the user's state. Because state lives in Pinia stores or in composables scoped to the dispatcher (not to each variant), unmounting and remounting a variant preserves state by construction. The change must verify this for at least `BookDetailsPage` (selected chapter, scroll position, panel tab) and `MainLayout` (side menu / right panel open state).
- Create the **Tablet variant file for every split surface in this change**, even though we are not designing the tablet layout yet. Initially each Tablet variant simply renders the Desktop variant (via `<component :is="Desktop" />` or equivalent), so behavior is unchanged but the scaffold is in place for a future tablet-specific layout.
- Split the following surfaces into dispatcher + 3 variants, preserving current behavior on every breakpoint:
  - **Layouts** — `layouts/MainLayout.vue` (currently mixes phone/tablet/desktop shell branches)
  - **Pages** — `pages/IndexPage.vue`, `pages/BooksPage.vue`, `pages/BookDetailsPage.vue` (largest; split work lives under `pages/book-details/`), `pages/AIPage.vue`, `pages/HelpPage.vue`, `pages/NotFoundPage.vue`
  - **Cross-cutting components with heavy per-device template divergence** — `components/novel/TranslationProgress.vue` (smoke-test target), `components/layout/AppRightPanel.vue`
- Trivial pages whose template is identical across devices today (`NotFoundPage.vue`) still get the dispatcher + 3 variants so the pattern is uniform; the three variant files may be near-identical at first.
- Non-layout, non-page components (e.g., `ParagraphCard`, `AppHeader`, dialogs like `ToastHistoryDialog`, `NovelScraperDialog`) keep their inline `isPhone` checks for now — they are leaf components whose divergence is mostly style tokens, not template structure. A follow-up change may split any that grow a full alternate template.
- Do **NOT** design or implement the tablet layouts in this change — tablet variants are scaffolds that re-use the desktop template today. A follow-up change fleshes them out.
- Do **NOT** change routing, Pinia store shapes, or user-visible behavior — this is a structural refactor.

## Capabilities

### New Capabilities

- `device-variant-dispatch`: Defines the dispatcher + three-variant (Desktop / Tablet / Mobile) component pattern — how a surface selects its device variant, **the Electron-always-Desktop override**, **the single shared dispatcher helper that encodes the selection rule (DRY)**, what a variant is allowed to contain, **the requirement that business logic is consumed from a shared per-surface composable rather than re-declared in each variant**, **the DRY rules for extracting shared UI fragments and sharing styles via tokens**, how shared state survives runtime breakpoint swaps, the rule that every layout and every page ships all three variant files (Tablet may initially re-use Desktop), and the exemption for leaf components whose divergence is style-only.

### Modified Capabilities

- `responsive-app-shell`: The app-shell requirement about "壳层切换" now additionally requires that phone, tablet, and desktop templates for a given surface live in separate variant components rather than inline `v-if` branches. Behavioral requirements (breakpoints, entry-point parity, context continuity) are unchanged.
- `responsive-book-details-workspace`: The book-details workspace must be expressed as a dispatcher that mounts the phone, tablet, or desktop variant of the workspace; the functional requirements (mode switching, context preservation, full-feature parity) are unchanged.

## Impact

- **Code structure**
  - New folder: `src/layouts/main-layout/` containing `MainLayout.vue` (dispatcher), `MainLayoutDesktop.vue`, `MainLayoutTablet.vue`, `MainLayoutMobile.vue`.
  - New folder: `src/pages/book-details/` containing `BookDetailsPage.vue` (dispatcher), `BookDetailsDesktop.vue`, `BookDetailsTablet.vue`, `BookDetailsMobile.vue`.
  - Other pages (`IndexPage`, `BooksPage`, `AIPage`, `HelpPage`, `NotFoundPage`) each get a sibling folder under `src/pages/<page-name>/` with dispatcher + three variants, following the same structure.
  - New sibling files per affected cross-cutting component — e.g., `TranslationProgressDesktop.vue`, `TranslationProgressTablet.vue`, `TranslationProgressMobile.vue` next to an updated `TranslationProgress.vue` dispatcher.
  - Tablet variants initially re-render the Desktop variant (placeholder), so they add file count but not template duplication until the tablet layout is designed.
  - **Per-surface composables** land under `src/composables/` (mirroring the page/layout folder — e.g., `composables/book-details/useBookDetailsPage.ts`, `composables/main-layout/useMainLayoutShell.ts`, `composables/translation-progress/useTranslationProgressPanel.ts`). These host all non-view logic for the surface so every variant consumes the same contract.
  - Existing composables under `composables/book-details/` and `composables/chat/` are reused / extended where possible; new ones follow the same naming (`use<Surface><Role>.ts`).
  - **Shared dispatcher helper** — a single `composables/useDeviceVariant.ts` (or equivalent `<DeviceVariant>` component) exposes the Electron-override + breakpoint resolution so every dispatcher is one line. The helper is the only place the selection rule appears.
  - **Shared UI fragments** — when variants of the same surface share a markup block, the block is extracted to a child component (preferred location: the surface's own folder, or `components/<surface>/`) rather than duplicated across variant files.
- **Routing**: `router/routes.ts` continues to point at the existing page paths — dispatchers keep the same component names / default exports. Layout registration in `router/routes.ts` continues to point at `layouts/MainLayout.vue` (the dispatcher).
- **Imports**: Any external importer of the affected SFCs keeps importing from the same path; the dispatcher preserves the public surface.
- **Electron parity**: The existing `bun run build:electron` output must continue to render the Desktop variant of every layout and page regardless of window size. Verified by resizing an Electron dev window below the phone breakpoint and confirming the Desktop shell + Desktop page variant remain mounted. The `useElectron()` composable (`src/composables/useElectron.ts`) is the source of truth the dispatcher consults.
- **Risk**: Regressions come from missed logic when moving code between files. Mitigated by landing one surface per commit, starting with `TranslationProgress` as the smallest non-trivial target, then `MainLayout` as the highest-leverage shell change, and running `bun run lint && bun run type-check` (plus manual phone + desktop + Electron-resize smoke tests) before each commit.
- **Not affected**: Stores, services, IndexedDB schemas, AI pipelines, i18n keys, leaf-component styles (styles move with their variant).
